# Model Thinking Streams for an Iliad Agent Chat

Research date: 2026-05-23

Scope: official current OpenAI and Google/Gemini API documentation for streaming progress, thinking, reasoning summaries, and opaque reasoning state. The product question is what Iliad can safely show in a clean chat UI while preserving provider-specific reasoning continuity for multi-step agent work.

## Executive Recommendation

Iliad should support a provider-neutral "progress stream" but should not expose raw chain-of-thought or opaque reasoning state. Render only:

- Assistant answer text.
- Provider-approved reasoning/thought summaries when explicitly requested and clearly labeled as summaries.
- Tool and file-operation progress generated by Iliad's own agent runtime.
- Final usage/cost/debug metadata in developer diagnostics, not in the default writing UI.

For v1, use a compact collapsible row such as `Thinking...` or `Reasoning summary` only when a provider emits an explicit summary stream. Otherwise show Iliad-owned statuses like `Reading Draft.md`, `Planning changes`, `Preparing patch`, and `Waiting for review`. The cleanest chat UI should prefer structured task/tool rows over long reasoning prose.

| --- | --- | --- | --- | --- | --- |
| OpenAI Responses API | Yes, opt-in with `reasoning.summary` on supported reasoning models. Summary appears in a `reasoning` output item `summary` array. | Yes, via `response.reasoning_summary_part.added`, `response.reasoning_summary_text.delta`, and `response.reasoning_summary_part.done` events. | Yes. Reasoning items should be preserved across tool/function turns; stateless mode can include `reasoning.encrypted_content`. | No. OpenAI docs state raw reasoning tokens are not visible via the API. | Show summaries only if explicitly enabled; never show `encrypted_content` or internal reasoning items. |

## OpenAI Responses API

OpenAI's reasoning models produce reasoning tokens internally. The reasoning guide says these tokens are not visible through the API, still consume context, and are billed as output tokens. It also says raw reasoning tokens are not exposed; applications can opt into a summary using `reasoning.summary`.

Relevant request shape:

```json
{
  "model": "gpt-5.5",
  "input": "Review this Markdown section for clarity.",
  "reasoning": {
    "effort": "low",
    "summary": "auto"
  },
  "stream": true
}
```

Non-streaming response shape for summaries:

```json
{
  "type": "reasoning",
  "summary": [
    {
      "type": "summary_text",
      "text": "..."
    }
  ]
}
```

Streaming event shapes relevant to a chat UI:

```json
{
  "type": "response.reasoning_summary_part.added",
  "item_id": "rs_...",
  "output_index": 0,
  "summary_index": 0,
  "part": {
    "type": "summary_text",
    "text": ""
  },
  "sequence_number": 1
}
```

```json
{
  "type": "response.reasoning_summary_text.delta",
  "item_id": "rs_...",
  "output_index": 0,
  "summary_index": 0,
  "delta": "...",
  "sequence_number": 2
}
```

```json
{
  "type": "response.reasoning_summary_part.done",
  "item_id": "rs_...",
  "output_index": 0,
  "summary_index": 0,
  "part": {
    "type": "summary_text",
    "text": "..."
  },
  "sequence_number": 3
}
```

Normal assistant text still arrives through standard response streaming events such as `response.output_text.delta` and `response.output_text.done`.

For tool-heavy work, OpenAI recommends preserving reasoning items across function-call turns so the model can continue its reasoning efficiently. If using `store: false` or zero data retention, the request can include `reasoning.encrypted_content`; returned reasoning items then have encrypted content that can be sent back on later turns. This is continuity state, not UI content.

OpenAI also documents an assistant message `phase` field for long-running or tool-heavy flows, with `commentary` for intermediate assistant updates and `final_answer` for completed answers. For Iliad, this is useful as a provider-side distinction between intermediate prose and final prose, but it should still be normalized into Iliad's own `assistant_progress` and `assistant_final` states.

### OpenAI Display Rules

Safe to show:

- `response.output_text.delta` as assistant answer text.
- `response.reasoning_summary_text.delta` only when summaries were explicitly enabled and the UI labels it as a summary.
- Tool call lifecycle and tool results, after Iliad validates and redacts them as needed.
- Usage counts, including reasoning-token counts, in diagnostics or expanded technical details.

Do not show:

- Raw chain-of-thought. OpenAI does not expose it as normal API output.
- `reasoning.encrypted_content`.
- Internal reasoning items used only to preserve tool-call context.
- Summary text as if it were guaranteed faithful, complete, or user-authored. It is a model-generated summary for insight/debugging.

## Gemini API

Gemini thinking models expose "thought summaries" as summarized versions of raw thoughts. The docs say to enable them with `thinkingConfig.includeThoughts: true`, then inspect response parts and check the `thought` boolean.

Relevant request shape:

```json
{
  "contents": [
    {
      "parts": [
        {
          "text": "Review this Markdown section for clarity."
        }
      ]
    }
  ],
  "generationConfig": {
    "thinkingConfig": {
      "includeThoughts": true
    }
  }
}
```

Non-streaming response handling:

```ts
for (const part of response.candidates[0].content.parts) {
  if (!part.text) continue;
  if (part.thought) {
    // Thought summary
  } else {
    // Answer text
  }
}
```

Streaming response handling:

```ts
const response = await ai.models.generateContentStream({
  model: "gemini-3.5-flash",
  contents: prompt,
  config: {
    thinkingConfig: {
      includeThoughts: true
    }
  }
});

for await (const chunk of response) {
  for (const part of chunk.candidates[0].content.parts) {
    if (!part.text) continue;
    if (part.thought) {
      // Rolling thought summary text
    } else {
      // Rolling answer text
    }
  }
}
```

Gemini content `Part` objects can also include:

```json
{
  "thought": true,
  "thoughtSignature": "...",
  "text": "..."
}
```

The `thoughtSignature` field is an opaque, base64-encoded signature for preserving reasoning context in later requests. Google says official Gen AI SDKs handle signatures automatically when using chat or appending the full model response object directly to history. Manual REST or custom history manipulation must pass signatures back exactly as received. The docs warn not to concatenate signed parts, merge signed and unsigned parts, or drop required function-calling signatures.

Gemini thinking controls affect raw thinking, not summaries. Current docs describe `thinkingLevel` for Gemini 3-family models and `thinkingBudget` for Gemini 2.5-family models. `minimal` lowers latency but does not guarantee no thinking for every complex task.

### Gemini Display Rules

Safe to show:

- Non-thought `part.text` as assistant answer text.
- `part.text` where `part.thought === true` only as a clearly labeled thought summary.
- Iliad-owned tool/file progress.
- `usageMetadata.thoughtsTokenCount` in diagnostics or cost details.

Do not show:

- `thoughtSignature`.
- Thought summary text as raw thoughts.
- Signed parts after modifying, concatenating, or re-chunking them.
- Function-call signatures or other provider continuity metadata in the transcript.

## Normalized Iliad Stream Model

Iliad should not bind the UI to provider event names. Normalize provider streams into a small internal event set:

| Iliad event | OpenAI source | Gemini source | UI treatment |
| --- | --- | --- | --- |
| `assistant_text_delta` | `response.output_text.delta` | `part.text` where `part.thought !== true` | Stream into assistant bubble. |
| `reasoning_summary_delta` | `response.reasoning_summary_text.delta` | `part.text` where `part.thought === true` | Optional collapsible summary row. Default collapsed or hidden in v1. |
| `reasoning_summary_done` | `response.reasoning_summary_part.done` | End of thought part/chunk accumulation | Finalize summary row. |
| `tool_call_delta` | Function/tool call streaming events | Function-call parts/chunks | Hidden from prose; render as structured tool row only after validation. |
| `tool_status` | Iliad runtime | Iliad runtime | Preferred user-facing progress surface. |
| `provider_state` | Reasoning items, encrypted content | `thoughtSignature` and signed parts | Persist for next request; never render. |
| `usage` | `usage.output_tokens_details.reasoning_tokens` | `usageMetadata.thoughtsTokenCount` | Diagnostics/cost details. |
| `error` | Provider error/incomplete events | Provider error/finish metadata | Actionable error row. |

## Product Implications for Iliad

### Clean Chat UI

The default transcript should not become a live dump of provider reasoning. For writing and document review, users need confidence and control more than a verbose mental trace. Use:

- A short running label: `Thinking`, `Reviewing selection`, `Preparing suggestions`.
- Structured tool rows for reads/searches/patch preparation.
- A final assistant answer with citations to file sections or proposed patch cards.
- Optional `Reasoning summary` disclosure for advanced/debug mode.

If summaries are enabled, avoid presenting them above the answer as the main progress indicator. Summaries can be distracting, can be imperfect, and may expose more detail than a user needs. The most useful default is a collapsed row with a short label and timestamp.

### Agent Continuity

Provider reasoning state should live in the agent session store, not in the visible chat message model:

- OpenAI: preserve reasoning items or use `previous_response_id`; include encrypted reasoning content only when needed for stateless operation.
- Gemini: preserve full signed parts or let the official SDK chat abstraction do it; never reshape signed parts casually.
- Iliad's transcript schema should separate `displayParts` from `providerState`.

This matters for document-native review because Iliad may run multi-step loops: read current file, inspect linked notes, draft a patch, receive user feedback, revise patch. Dropping provider state can increase cost, degrade tool-call performance, or trigger Gemini validation errors.

### Safety and Trust

Reasoning summaries are safe enough to display when explicitly requested by the application, but they should be treated as summaries, not raw truth. They may contain irrelevant, speculative, or overly technical content. For a prose editor, the stronger trust surface is evidence:

- Which files were read.
- Which selection was used.
- What patch is proposed.
- Why the change helps the document.
- What the user can accept, reject, or revise.

This suggests a v1 default of hiding provider summaries and showing Iliad-authored progress rows. Add a developer or advanced preference later: `Show model reasoning summaries when available`.

### Recommended Defaults

- OpenAI: request `reasoning.summary: "auto"` only for debug builds, developer diagnostics, or difficult agent tasks where a summary materially helps review. Do not enable it globally in the normal writing chat until the UI has a good disclosure pattern.
- Gemini: keep `includeThoughts` off by default. Enable it for diagnostics or "explain approach" mode, and route `part.thought` text to a summary disclosure rather than the main answer.
- Both providers: store opaque reasoning continuity data separately and redact it from logs that might be exported with the user-facing conversation.
