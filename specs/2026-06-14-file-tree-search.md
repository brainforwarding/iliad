# File Tree Search

Date: 2026-06-14
Status: research-backed product/implementation spec, expert-reviewed and revised
Scope: VS Code-like search and filtering inside the Iliad file tree.

## Problem

Iliad's file tree is easy to scan in small writing projects, but it does not
scale once a workspace has many folders, drafts, generated assets, or pending
agent-created documents. Users need a local, fast way to find a file or folder
without leaving the file tree, opening global content search, or using the
agent.

The feature should feel familiar to people who use VS Code's Explorer find
control: a compact find UI attached to the tree, live matching while typing,
keyboard navigation through matches, highlight and filter modes, and fuzzy
matching as an explicit mode.

## Research Summary

Best current fit:

1. Mirror VS Code's tree find behavior, not workspace content search. VS Code's
   Explorer can open a Find control with `Option+Command+F` on macOS or
   `Ctrl+Alt+F` on Windows/Linux, type part of a file or folder name, switch
   between highlighting and filtering, use Down to focus the first match, show
   folder badges for matching descendants in highlight mode, and toggle fuzzy
   matching. Sources: [VS Code user interface docs](https://code.visualstudio.com/docs/editing/userinterface#_advanced-tree-navigation),
   [VS Code 1.70 tree find control](https://code.visualstudio.com/updates/v1_70#_tree-find-control),
   [VS Code 1.94 Find in Explorer](https://code.visualstudio.com/updates/v1_94#_find-in-explorer).
2. Preserve VS Code's later usability refinements where they are cheap: remember
   the last search term while the control is reopened in the same app session
   and keep keyboard navigation vertical. Source:
   [VS Code 1.72 tree find improvements](https://code.visualstudio.com/updates/v1_72#_tree-view-find-control-improvements).
3. Treat this as a tree-view accessibility problem, not just a styled input.
   WAI-ARIA's tree view pattern separates focus from selection, recommends
   arrow-key navigation, type-ahead for larger trees, explicit `tree` /
   `treeitem` roles, `aria-expanded` for parent nodes, and visible distinction
   between focus and selection. Source:
   [WAI-ARIA APG Tree View Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/).

## Recommendation

Build a renderer-only file-tree search control in `FileTree`. It should search
the already-loaded `FileTreeDisplayNode[]` generated by
`buildFileTreeDisplayNodes`, including real files, real folders, pending create
nodes, and pending virtual directories.

```text
FileTree display nodes
  -> flatten searchable index with ancestor paths
  -> query matcher: continuous or fuzzy
  -> match metadata: self ranges, descendant count, active match order
  -> rendered tree: normal highlight mode or filtered tree mode
  -> TreeRow receives search metadata and renders match marks/badges
```

This is not an IPC feature. The app already has the file tree in the renderer,
so searching does not need filesystem calls, main-process changes, or persistence
outside local UI state.

## Goals

- Add a compact find control to the file tree.
- Open it with a sidebar action and with VS Code-like shortcuts.
- Search file and folder display names, including Markdown stems that hide
  `.md` in the current UI.
- Include pending agent-created files and pending virtual directories in search.
- Support highlight mode and filter mode.
- Support continuous matching and fuzzy matching.
- Let users navigate matches with keyboard and small icon buttons.
- Keep search state local to the sidebar and reset safely on workspace switch.
- Preserve user expansion state when the search closes.
- Keep file opening, folder expansion, pending proposal opening, and row
  selection behavior consistent with the current tree.
- Add focused pure tests for matching/filtering helpers and a manual QA checklist
  for keyboard behavior. Add component-test tooling only if a later
  implementation explicitly chooses that route.

## Non-Goals

- No document-content search.
- No global workspace search panel.
- No indexing service, database, ripgrep, or Electron main-process file walk.
- No replace.
- No multi-select search actions.
- No search history across app launches.
- No fuzzy scoring that reorders the tree. Tree order remains the existing
  folder/Markdown/assets/external sort order.
- No new color palette. Add semantic tokens only if existing tokens are
  insufficient.

## UX

### Entry Points

- Add a search icon button to `.sidebar-actions`, using lucide `Search`.
- Order header actions as Search, New document, New folder. The workspace name
  may ellipsize to keep the action buttons stable.
- Tooltip / aria label: `Find in file tree`.
- Keyboard shortcuts:
  - macOS: `Option+Command+F` when the sidebar or file tree has focus.
  - Windows/Linux: `Ctrl+Alt+F` when the sidebar or file tree has focus.
  - Optional convenience after manual verification: `Command+F` / `Ctrl+F` only
    when focus is already inside the file tree and not inside rename/search text
    input. Do not steal editor find.
- Shortcut focus guards:
  - ignore `input`, `textarea`, `select`, and `[contenteditable]`;
  - ignore active rename and active search inputs;
  - require `sidebarRef.current.contains(document.activeElement)`;
  - never register the tree find shortcut from CodeMirror/editor focus.
- Opening search focuses the query input and selects the previous in-session
  query, matching VS Code's "remember last search text" behavior.
- Opening search while the control is already open focuses and selects the query
  input. The search button and shortcut do not toggle the control closed.
- Opening search closes the tree context menu. If a rename input is active, do
  not intercept the shortcut; let rename finish/cancel normally.
- Track the actual previously focused `HTMLElement` when opening search. Restore
  it if still connected and focusable; otherwise fall back to the search header
  button.

### Control Layout

Use a compact control in its own sidebar grid row directly under the sidebar
header:

```text
[query input with embedded search icon...........] [x]
[1/7] [fuzzy] [filter]                 [prev] [next]
```

Implementation notes:

- Keep it within the 276px desktop sidebar and the 220px narrow responsive
  minimum. Do not use a large card, modal, or assistant-style surface.
- Put the search icon inside the input instead of spending a separate button
  column inside the open control.
- Use 26-30px icon buttons. The count should be compact (`1/7`) visually, with
  a fuller localized aria label such as `Match 1 of 7`.
- At narrow widths, keep the input row intact and allow only the second control
  row to wrap. Do not let controls shrink the query input below a usable width.
- Use `role="search"` on the wrapper and `type="search"` for the input.
- The count is secondary text. Use `No results` only when query is non-empty and
  there are zero matches.
- The fuzzy and filter controls are icon toggles with `aria-pressed`.
- Do not use an `Aa` icon for fuzzy matching because it conventionally means
  case sensitivity. Use a distinct search/fuzzy icon such as lucide `ScanSearch`,
  with tooltip and aria text carrying the exact meaning.
- Use `data-tooltip` for icon labels; do not add explanatory app copy.
- `Escape` closes the control, restores normal tree rendering, and stops event
  propagation so app-level Escape handlers do not also fire.
- `Clear` (`x`) clears the query but keeps the control open.
- When query is empty, filter/highlight toggles remain visible but inert.
- Closing with `Escape` restores the saved focus target, falling back to the
  search header button.

Rationale: VS Code uses a floating find widget, but Iliad's file tree is narrow
and already has a calm rail layout. An in-tree control keeps the same
interaction model without covering filenames or fighting narrow mobile widths.

### Matching Modes

Continuous mode:

- Case-insensitive contiguous substring match against the display name.
- Example: `chap` matches `Chapter 1`; `ct1` does not.

Fuzzy mode:

- Case-insensitive ordered-character match against the display name.
- Example: `ct1` matches `Chapter 1` because `c`, `t`, and `1` appear in order.
- Preserve tree sort order; fuzzy match quality affects highlighting only, not
  ordering.

Default:

- Fuzzy matching on by default, because VS Code's current Explorer find exposes
  fuzzy matching as a first-class search mode and it is better for large writing
  trees.
- The user can toggle to continuous mode for more precise matching.

Path behavior:

- Phase 1 matches display names only, because VS Code documents the Explorer
  find feature as matching file or folder names.
- If the query contains `/` or `\`, treat those characters as ordinary display
  name query characters in Phase 1. This usually produces normal `No results`;
  do not silently switch to hidden path matching.

Normalization:

- Trim leading/trailing whitespace for matching.
- Collapse internal whitespace in the query to a single space.
- Use locale-safe lowercasing.
- Phase 1 is accent-sensitive. Add diacritic-insensitive matching only if it can
  preserve correct highlight ranges without brittle index math.

### Highlight Mode

Highlight mode is the default rendering mode.

- Keep the tree structure and user-expanded folders as-is.
- Highlight matching character ranges in the row label.
- If a collapsed folder contains matching descendants, show a compact descendant
  count immediately after the folder name.
- If an expanded folder contains matching descendants, it may still show the
  count only when the folder itself does not match. This avoids visual noise on
  rows that already have highlighted text.
- The active match row gets a search-active treatment distinct from active/open
  file, selected row state, and keyboard focus.
- `Enter` in the search input reveals the next match. It must not open a file or
  change the editor document.
- `Shift+Enter` reveals the previous match.
- `ArrowDown` from the search input focuses the current/first matched row.
- `ArrowUp` from the search input focuses the previous matched row.
- `ArrowDown` / `ArrowUp` from a focused row while search is open move between
  matched row buttons.
- Clicking a row, pressing `Enter` while a row has focus, or using the row's
  existing activation behavior opens the file/folder/pending proposal.

If the active match is inside a collapsed folder, transiently expand ancestor
folders to reveal it. This expansion exists only while search is active unless
the user explicitly toggles a folder.

### Filter Mode

Filter mode hides non-matching leaves while preserving context:

- Render rows that match themselves.
- Render ancestors of matching descendants.
- Render descendants only if they match or are ancestors of matches.
- If a directory name matches, keep that directory's normal descendants
  available when it is expanded. This avoids a matching folder opening into an
  apparently broken empty subtree.
- Transiently expand all matching ancestor paths so users can see results.
- Keep each row at its normal tree depth. Do not flatten into a search-results
  list.
- Show the same match highlights as highlight mode.
- If query becomes empty, return to normal tree rendering immediately.
- Closing search restores the expansion set the user had before search opened,
  plus any folders the user explicitly toggled while search was open.

During active filter mode with a non-empty query:

- Opening files and folders remains enabled.
- Dragging context Markdown files remains enabled.
- Context-menu actions remain enabled for visible real nodes, including rename,
  duplicate, copy path, reveal in Finder, and move to trash.
- Starting rename from a filtered result closes search first so the rename row
  cannot disappear mid-edit.
- Pending and virtual rows keep today's behavior: no context menu actions.

### Tree Keyboard Behavior

The current tree renders each row as a normal button and does not yet implement
a full ARIA tree. Do not add `role="tree"` / `role="treeitem"` in Phase 1 unless
the same implementation also converts the tree to a proper one-focus-target
roving-tabindex widget and tests the full keyboard contract.

Phase 1 search should keep the existing button semantics and add only the
keyboard behavior needed for the find control:

- Search input `Enter` / `Shift+Enter`: reveal next/previous match.
- Search input `ArrowDown` / `ArrowUp`: move DOM focus to the matched row's
  existing button.
- Maintain refs to the actionable `.tree-open-button` elements, not only row
  wrapper divs.
- Focused row `Enter` / click: use existing row activation behavior.
- Focused row `Escape` while search is open: return focus to the search input.
- Search-owned `Escape`, `Enter`, and arrow-key handlers call
  `preventDefault()` and `stopPropagation()`.
- Keep selected/open-file state visually distinct from keyboard focus and search
  active match state.

Full ARIA tree behavior is a follow-up, not a hidden prerequisite for file-tree
search. If implemented later, it should support roving `tabIndex`, `aria-level`,
`aria-expanded` on directories, `ArrowUp` / `ArrowDown`, `ArrowLeft` /
`ArrowRight`, `Home` / `End`, and printable type-ahead per the WAI-ARIA tree
view pattern.

The search control preserves normal text-input editing while focused except for
`Enter`, `Shift+Enter`, `ArrowDown`, `ArrowUp`, and `Escape` as defined above.

## Data Model

Pure helper types:

```ts
export type FileTreeSearchMode = "continuous" | "fuzzy";

export interface FileTreeSearchMatch {
  id: string;
  path: string;
  relativePath: string;
  displayName: string;
  selfRanges: Array<{ start: number; end: number }>;
  ancestorPaths: string[];
}

export interface FileTreeSearchNodeMeta {
  selfMatch: boolean;
  selfRanges: Array<{ start: number; end: number }>;
  descendantMatchCount: number;
  visibleInFilter: boolean;
}

export interface FileTreeSearchResult {
  normalizedQuery: string;
  matches: FileTreeSearchMatch[];
  metaById: Map<string, FileTreeSearchNodeMeta>;
  filterAncestorPaths: Set<string>;
}
```

`id` should come from one canonical helper, such as `displayNodeId(node)`, and
should currently equal the display path used by row and row-button refs. The key
point is that all helpers and components use the same identity function for real
filesystem nodes and synthetic pending nodes.

Component state:

```ts
interface FileTreeSearchState {
  open: boolean;
  query: string;
  mode: FileTreeSearchMode;
  filter: boolean;
  activeMatchIndex: number;
}
```

Keep a `searchReturnFocusRef: HTMLElement | null` outside serializable state.
Keep the last query/mode/filter values in React state while `FileTree` remains
mounted. On `workspace.path` change, close search and reset query, mode, filter,
and active match index to defaults.

## Implementation Plan

### Phase 1: Pure Search Helpers

- Export canonical display-node helpers before implementing search:
  - `displayNodeId`
  - `displayNodePath`
  - `displayNodeRelativePath`
  - `displayNodeName`
  - `displayNodeKind`
  - `displayTreeName`
- Add `src/assistant/fileTreeSearch.ts`.
- Export helpers that accept `FileTreeDisplayNode[]` and use the canonical
  accessors so helper tests and row rendering cannot drift.
- Flatten all display nodes with:
  - `id`
  - `path`
  - `relativePath`
  - display name
  - kind
  - source
  - ancestor paths
  - original node reference if needed
- Implement continuous and fuzzy matchers.
- Compute match order as preorder traversal of the current sorted display tree.
- Compute descendant counts by walking back through ancestor paths for every
  self match.
- Compute filter visibility from self matches plus ancestors of self matches.
- Return a pruned recursive display tree for filter mode, or a recursive
  visibility helper. Filtering only the top-level array is insufficient.
- Unit-test real nodes, pending creates, pending dirs, Markdown stem matching,
  collapsed ancestor metadata, no-query behavior, continuous matching, fuzzy
  matching, and stable tree-order match ordering.

### Phase 2: FileTree Integration

- Add search state to `FileTree`.
- Add `Search` button to `.sidebar-actions`.
- Add keyboard listener scoped to the sidebar/tree root, not `window`, unless
  needed for Electron shortcut consistency.
- Add `onCloseContextMenu` to `FileTreeProps` and call it when search opens.
- Render `FileTreeSearchControl` when search is open.
- Derive `searchResult` with `useMemo`.
- Derive `renderedNodes` from `displayNodes` plus recursive filter metadata.
- Refactor expansion state before adding search:
  - rename current durable state to `durableExpanded`;
  - preserve existing one-shot pending/reveal expansion behavior by adding those
    paths to `durableExpanded` when the app intentionally wants the opened state to
    stick;
  - introduce `searchForcedExpanded`, derived only from the active match and
    filter ancestors while search is open.
- Derive `effectiveExpanded = durableExpanded ∪ searchForcedExpanded`.
- If the user toggles a folder while search forces it open, update
  `durableExpanded` but keep the folder visibly open until the search no longer
  forces it. Closing search then reveals the user's recorded expanded/collapsed
  state.
- When search closes, clear active match index and `searchForcedExpanded`.

### Phase 3: Row Rendering

- Pass search metadata into `TreeRow`.
- Render highlighted name by splitting `displayTreeName(node)` into text and
  `<mark className="tree-search-mark">` segments.
- Add a descendant count in a non-competing location inside the name column,
  immediately after the text label. Do not reuse the existing 18px trailing slot,
  because pending dots and external-link hints already use it.
- Preserve existing trailing indicators:
  - pending dot remains in the trailing slot;
  - external-link hint remains available when there is no pending dot;
  - search descendant count can appear at the same time as a pending dot.
- Add active-search-match class separate from `is-active` and `is-selected`.
- Ensure pending-created files can be opened from search results via
  `onOpenPendingChange`.

## Edge Cases

- Empty tree: search can open; input is enabled; tree still shows `No files`.
- Query has no matches: show `No results`; do not mutate expansion.
- Active file hidden by filter: keep editor unchanged; selected/open file can be
  hidden while filter is active.
- Workspace switch: deterministically set `open=false`, `query=""`,
  `mode="fuzzy"`, `filter=false`, and `activeMatchIndex=-1`.
- Rename in progress: search shortcut does not activate while rename input has
  focus.
- Rename starts from a context menu action by closing search before the rename
  input appears.
- Context menu open: opening search closes the context menu through the
  `onCloseContextMenu` prop because the menu is owned by `App`.
- Search query, fuzzy-mode, or filter-mode changes also close the context menu,
  because the menu may otherwise remain over a hidden row.
- Pending proposal status changes: search recomputes from new `displayNodes` and
  clamps active match index.
- Search query changes while active match was inside a transiently expanded
  folder: recompute active match and transient expansions from scratch.
- Folder toggle during search: user toggles update `durableExpanded`; search
  transient expansions remain additive until search closes.
- Hidden external/assets nodes: search includes them if the file tree already
  renders them. Do not introduce new inclusion/exclusion rules.
- Pending dot plus search descendant count: both must remain visible; the search
  count lives beside the filename, not in the status slot.
- Search closed with `Escape`: restore focus to the invoking button or previous
  row. If that row no longer exists, focus the search header button.

## Open Questions

- Should filter/fuzzy preferences persist per workspace after users have muscle
